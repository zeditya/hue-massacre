# HUE MASSACRE — Project Structure

This is the **real** tree, not a plan. The project deliberately does not look like
a typical Godot game: there is **one scene**, and everything else is code.

```
res://
├─ project.godot             entry point, input map, window, Compatibility renderer
├─ export_presets.cfg        the Web export preset (single-threaded)
├─ LICENSE                   MIT — covers the code, NOT the art in assets/
├─ README.md / TESTING.md / HOW_TO_RUN.md
├─ GAME_SPEC_v3.md           the locked source of truth for the rebuild
├─ docs/
│  ├─ level_plans.png        generated by tools/make_floor_plans.gd
│  ├─ AI_CHAT_HISTORY.pdf    the merged AI transcript (graded deliverable)
│  ├─ README.md              how that PDF was assembled + checklist
│  └─ proto/2d_camera/       screenshots from the rejected camera prototype
├─ assets/
│  ├─ characters/adventurer/ the ONLY imported art the game draws with
│  ├─ tiles/                 the first build's floor tiles (kept, now unused)
│  ├─ LICENSES/              the licence text for each art pack
│  └─ ATTRIBUTION.md         where every asset came from, and its terms
├─ scenes/
│  └─ main.tscn              the whole game: one Node + scripts/game.gd
├─ scripts/
│  ├─ game.gd                conductor: state machine, score/combo, camera, juice
│  ├─ color_theory.gd        ALL hue maths (gaps, complements, mixing, contrast)
│  ├─ level_data.gd          all 4 arenas as plain dictionaries
│  ├─ room.gd                builds an arena from its dictionary; runs the rules
│  ├─ arena_art.gd           the look: baked sand, masonry, stands, banners, braziers
│  ├─ player.gd              the Unsworn: movement, strike chain, roll, absorption
│  ├─ guard.gd               knights: AI, detection, attacks, the Champion's phases
│  ├─ paint_layer.gd         splats, fading, "what colour is the floor here?"
│  ├─ mote.gd                colour pickups
│  ├─ sprite_bank.gd         slices the character sheets into SpriteFrames
│  ├─ tile_bank.gd           the old tiled floor (flat-grey fallback)
│  ├─ hue_tint.gdshader      recolours a character to ANY hue
│  ├─ darkness.gdshader      the dark arena: torch beam + knight lanterns
│  └─ audio_bank.gd          every sound effect, synthesised at runtime
├─ ui/
│  ├─ ui_style.gd            fonts + palette + the type scale, in one place
│  ├─ hud.gd                 vigour, hue swatch, wheel strip, waves, boss phase
│  └─ screens.gd             pause / victory / defeat — the only three pages
├─ tests/

│  └─ test_runner.tscn       a tiny scene to run them
├─ tools/

│  ├─ make_floor_plans.gd    draws docs/level_plans.png from level_data.gd
│  ├─ preview_floor.gd       checks the old tiled floor's average colour
│  └─ capture.gd             renders a frame of each arena (needs a display)
├─ proto/2d/                 the archived camera prototype (on master)
└─ build/                    GITIGNORED: captures, web export, throwaway scripts
```

## Why it is shaped like this

| Piece | Why it exists |
|---|---|
| `scenes/main.tscn` | One node. Every other object — arenas, knights, the player, the HUD, the pages, the darkness — is created in `_ready()` of a script. There is nothing to break by mis-clicking in the editor. |
| `level_data.gd` | **The level design is data.** Four arenas as dictionaries: walls, motes, braziers, wave plan and knight specs. The test suite reads the *same* function (`LevelData.walls_for`) the game builds with, so a level can never be tested against different geometry from the one it runs with. |
| `color_theory.gd` | Every rule in the game in one file of static functions, so the marking core can be read top to bottom. |
| `guard.gd` | One class for every enemy, including the Champion. The archetypes (Aspirant / Warden / Harrier) are **stats in `level_data.gd`**, and the boss is a flagged branch, so there is exactly one AI to understand. |
| `arena_art.gd` | The whole look, separated from the rules. Nothing in this file can change gameplay — it only draws. |
| `ui/` | Presentation only. `ui_style.gd` owns the palette and type scale so the HUD and the pages cannot drift apart. |
| `tests/` | Run headless by CI and by hand; excluded from the web export via `export_presets.cfg`. |
| `tools/` | Generators and dev-only checks. Nothing here ships inside the game. |
| `build/` | Entirely gitignored: captures, throwaway `shot_*.gd` scripts and the web export output. |

## The moving parts, at a glance

- **Flow:** `game.gd` starts a run immediately (there is no menu), builds arena 1
  through `room.gd`, and advances on `room_cleared`.
- **Arena → game:** `room.gd` reports `guard_killed`, `player_died`, `room_cleared`,
  `wave_started`, `wave_cleared`, `boss_vulnerable_changed`, `boss_phase_changed`,
  `boss_summons_spawned`, `boss_charge_started` and `strike_landed`. `game.gd` is
  the only listener, so all scoring and feedback lives in one file.
- **Player → arena:** the player emits `struck`, `rolled`, `hurt`, `died`; the room
  answers a strike with auto-aim and noise, and resolves the hit.
- **Who decides a kill:** only `room._on_guard_killed`. Every path into a death
  (blade, scripted kill, test shortcut) spills paint, feeds the player's hue and
  updates the wave state in that one place.

## Conventions worth keeping

1. **Tabs, not spaces** (see `.editorconfig`).
2. **Every tunable is an `@export`** at the top of its script, in a group, so it can
   be tweaked live in the editor.
3. **Comment the *why*, in plain language.** The code is meant to be explained line
   by line in the video.
4. **Verify every data edit**, then re-run the suite:
   `godot --headless --path . res://tests/test_runner.tscn` → `385 passed, 0 failed`.
5. **Headless green is not visually right.** The suite never executes `_draw()`.
   Render a frame (`tools/capture.gd`) after any visual change.
6. **New `class_name`?** Run the editor once (`godot --headless --editor --path . --quit`)
   before running the suite headless, or the type will not resolve. See TESTING.md §6.
